# Cloudtrail of Crumbs

Cloud platforms keep a diary on your behalf. Every API call against
an account, whether it comes from a laptop in the office or a stolen
laptop somewhere else, lands in one append-only stream with a
timestamp, a caller identity, a source address, and the exact action
requested. Incident responders treat that stream as the ground truth
of an intrusion because memory can be wiped and malware can lie, but
the control plane log records what actually happened to your
resources. In this room you play the responder. A backup bucket named
nimbus-prod-backups spent part of the night serving its contents to
whoever asked, and the exported audit trail holds the whole story:
one leaked key, one assumed role, one minted access key, one policy
rewrite. Your job is to pull those four moments out of the noise,
name the identities involved, and file a report precise enough that a
colleague could act on it without re-reading the raw events.

## What is real here, and what is simulated

Nothing in this lab talks to a cloud provider. The evidence file at
/evidence/cloudtrail-sim.json is static JSON shipped inside the
container, generated by hand so every field is deterministic across
restarts, and the event names use a sim.* namespace instead of any
vendor's exact wire format. The report desk is a single Flask route
that compares three query parameters against constants and prints the
room flag when all three match. What is faithful is the analytical
work, not the plumbing: real audit exports really do arrive as long
JSON arrays mixing routine automation with the few events that
matter, identities really are described with type and user name and
access key fields, and sourceIPAddress really is the fastest way to
spot a stranger in your account. Treat the sim prefix as an honest
label rather than an obstacle. The reasoning you practice here
transfers unchanged when the log says cloudtrail.amazonaws.com and
the bucket policy statement ends up in a real incident ticket.

## Reading an audit trail like an investigator

Start by establishing normal before hunting for abnormal, because an
audit log is only suspicious relative to a baseline. Read the earliest
events and notice the rhythm: ci-deployer lists objects, fetches a
nightly archive, uploads a manifest, always from 10.44.0.15, always
with the same access key. That rhythm is the automation doing its job.
Once the baseline is set, every deviation becomes visible, and the two
deviations worth watching in any such log are source address and
action type. An identity calling from an address outside the office
range deserves a question even if the action looks harmless, because a
valid key used from the wrong network usually means the key left the
building. Then watch the sequence of actions rather than each event in
isolation. A read followed by assume_role followed by create_access_key
followed by put_bucket_policy is not random; it is a ladder where each
rung raises the attacker's standing. Investigators call this
progression, and naming each rung in order is exactly what the report
desk asks of you.

## From first anomaly to full chain

Walk the timeline from 02:47 forward and narrate each step as if you
were testifying. The first outside get_object reuses AKIASIMDEPLOY01,
the long-lived key belonging to ci-deployer, which answers who was
impersonated and which credential leaked. Minutes later the same
address calls assume_role on log-archive-reader and receives session
credentials, showing the thief wanted broader permissions without
touching the original key again. The create_access_key event is the
persistence moment: requestParameters.userName names backup-archiver
as the beneficiary, and responseElements hands back AKIASIMPERSIST77
marked Active, a brand-new key the legitimate owner never requested.
Finally put_bucket_policy carries the payload, and its response embeds
the document that matters, a statement with Principal * granting
GetObject and ListObjects on everything in the bucket. The two
anonymous downloads that follow, from yet another address, confirm the
policy took effect. Answering the three report questions correctly is
then mechanical, and the desk closes the case by printing your flag.

## Scope

Work only against http://target:8000 inside your own lab instance.
The evidence endpoint serves a fixed file, the report endpoint reads
query parameters, and neither reaches anywhere else; there is no route
to the internet, other labs, the host, or the control plane. Nothing
in this room requires brute force, scanning beyond your own target,
or automated guessing against the report desk, since every answer is
printed plainly in the log once you read carefully. The credentials,
key identifiers, and addresses in the evidence are invented values
that exist only inside this container, so there is nothing to reuse
against real systems and no reason to try. If an answer does not
verify, go back to the events rather than hammering the desk; the log
contains the exact spelling of every correct value. That habit, of
treating evidence as the arbiter instead of guesswork, is the one
this room exists to build.
