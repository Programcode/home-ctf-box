# Platform integration matrix

How OpenRange relates to the CTF frameworks, training labs, vulnerable distributions, and blue-team ranges people ask about most. The brief named 53 projects; Metasploitable 2 and 3 get separate rows because they are different products, so the table carries 54.

Mapping came from project knowledge only, no web lookups. Entries tagged (thin docs) are projects whose public documentation I cannot characterize precisely from memory. They are mapped at the generic level their names imply and should be re-checked against the live product before anyone builds something specific for them.

## Coverage model

OpenRange covers outside platforms four ways.

- Covered-native. A shipped OpenRange capability delivers the same mechanic. Citations name an endpoint file under `apps/api/src/openrange/api/`, a contract under `docs/contracts/`, or a decision record.
- Inspired. An existing original room or module teaches the same mechanic with its own scenario, text, and code. Nothing is copied from the source platform.
- Planned-wrap. The right answer is a wrapper bundle: a thin `content/rooms/*` bundle declaring an `external_image` entry that orchestrates the upstream project's official image through the normal lab lifecycle, graded with derived per-session flags (docs/decisions/0007-flag-derivation.md). This mechanism does not exist in the repo yet. A repo-wide search finds zero `external_image` entries under `content/`. Every planned-wrap row waits on gap 11 below, so the wrapped count in this matrix is honestly 0 today.
- Planned-new. Nothing ships today in any form. Each case appears in the gap analysis with an issue-sized next step.

### Licensing stance

What we wrap. Only images published by the upstream project itself, referenced by immutable digest, pulled at deploy time, never vendored into this repository. Each wrapper states the upstream license in its bundle metadata per the per-bundle license rule (docs/decisions/0006-content-packaging.md, docs/content-licensing.md). Trademarks stay with their owners and wrapper titles remain original, as docs/content-licensing.md already requires for room names.

What we never do. Redistribute virtual machine images from catalogs like VulnHub or HackMyVM, vendor third-party appliances into our registry, or clone copyrighted challenge levels and writeups, including close paraphrases (docs/content-licensing.md contribution rule). Commercial catalogs such as VulnLab stay out of scope unless the vendor publishes a compatible license or signs a partnership.

## Gap analysis

Each item names what exists today with proof, then an issue-sized next step.

1. Attack-defense king-of-the-hill mode (echoCTF.RED, FBCTF). Rooms are single-player targets today; a repo-wide search for attack-defense or king-of-the-hill returns nothing relevant. Next step: a decision record plus schema work, a shared cohort-facing target with a capture timer, then scoring hooks.
2. Hint economy beyond tiers (RootTheBox). Hints are ordered tiers with declared costs revealed through POST /api/learning/hints/{room_slug}/{task_ref}; there is no wallet or spend ledger. Next step: a hint wallet whose spends show up in GET /api/scoring/me/score and admin score adjustments.
3. Achievement toast UI. GET /api/scoring/me/achievements ships and the web app has a toast primitive (ToastProvider in apps/web/app/layout.tsx, useToast in apps/web/components/LabPanel.tsx), but nothing connects them. Next step: fire a toast when an achievement lands and add a badge shelf to the profile page.
4. Challenge file download portal (Crackmes.one, CyberDefenders, BlueTeamLabs). The API exposes no attachment or download endpoints (searching apps/api/src for attachment, download, artifact returns nothing) and the gateway proxies only ports and terminals. Next step: signed, lab-scoped evidence downloads through the gateway plus a files panel on the room page.
5. Randomized per-instance vulnerable apps (SecGen). create_instance builds exactly what the bundle ships. Next step: a bundle-level randomization manifest covering ports, credentials, and file trees, substituted at creation time with solver regeneration.
6. Network-capture replay labs (CyberDefenders). Modules teach tshark workflows against static text, no room replays a capture as traffic. Next step: a replay target image plus an investigation validator type keyed on flags embedded in artifacts.
7. Crackme-style reverse boards (Crackmes.one). Reverse engineering coverage is lesson-plus-quiz modules; no graded binaries. Next step: a binary attachment type that embeds a per-session flag at provision time, reusing the derivation in docs/decisions/0007-flag-derivation.md so each download validates uniquely.
8. Learner-facing code-review challenges (Code Review Lab). Next step: a code-review validator comparing a findings list, authored through studio drafts with seeded diffs.
9. OSINT challenge type. Zero matches for osint across apps, content, packages, and contracts. The schema accepts arbitrary tracks, five exist today, so the next step is an osint track with simulated personas, a scope policy forbidding real-person targeting, and one pilot room.
10. Team-vs-team red/blue scoring split (echoCTF.RED, FBCTF, VulnArena). Next step: a team entity, split scoreboards, and role-based objectives feeding GET /api/scoring/leaderboards/{scope}.
11. Wrapper-bundle mechanism. No external_image support exists anywhere in content or packages. This gates every planned-wrap row above. Next step: a schema field with digest pinning, a license allowlist, and a CI policy test rejecting unpinned or unlicensed references.
12. Dynamic score decay (CTFd, Mellivora). Points are static integers in room.yaml. Optional next step: a time-decay option in the scoring projection service.
