# Localization framework (i18n)

English is the source of truth for all curriculum content. Translations
ship as optional override files next to a module manifest and may only
carry translatable prose; machines-readable fragments are protected and
validated. This document describes Phase 8 item 8: what ships today,
how contributors add or review a locale, and how the API serves it.

## Layout

A module directory holds its English manifest plus one optional override
file per locale:

```
content/modules/<slug>/
  module.yaml          # English source of truth
  sections.hu.yaml     # Hungarian overrides (optional)
  sections.de.yaml     # German overrides (optional)
```

Override files contain only `locale` and `sections`. Each entry targets
one section by `id` and carries the translated `title` plus translatable
blocks (`prose`, `callout`) in document order. Code and quiz blocks are
never listed; they stay English-owned and are copied through untouched.

```yaml
locale: hu
sections:
  - id: navigate-with-intent
    title: 'Navigálás szándékkal'
    blocks:
      - type: prose
        markdown: |
          ...
      - type: callout
        tone: tip
        markdown: |
          ...
```

The loader validates entries with the same `Section` model as the
manifest and rejects unknown top-level keys, wrong `locale` declarations,
duplicate section ids, non-translatable block types, and block-count
mismatches against the source section.

## Protected spans

Translations must copy these verbatim from the English source:

- fenced code blocks (` ``` `)
- inline code (`` `like this` ``)
- command lines (`$ grep -rn ...`)
- CLI flags (`-v`, `--force`)
- filesystem paths (`/var/log`, `./lab/raw`, `~/lab`)

`openrange.content.i18n.validate_translation(original_block,
translated_block)` extracts every protected span from the source block
and requires each to appear verbatim in the translation. A near-identical
counterpart reports a `modified` violation; an absent span reports
`missing`. The function returns a list of `Violation(kind, span_kind,
expected, detail)`; an empty list means the translation is faithful.
Contributors run it before opening a PR, and CI runs it again over every
override file in the repository (see
`packages/content-sdk/tests/test_i18n.py::test_shipped_hungarian_sample_passes_validation`
for the shipped proof).

## Locale resolution

`resolve_locale(requested, available)` resolves in three steps:

1. exact tag match (`hu` when `hu` is available),
2. language fallback (`hu-HU` to `hu`),
3. default `en` — the English base content.

Available locales come from the `sections.<locale>.yaml` files found in
the module directory; English always counts as available.

## Contributor review workflow

1. Copy the translatable blocks out of `module.yaml` into a new
   `sections.<locale>.yaml`; translate titles and prose only. Keep every
   protected span byte-identical, including whitespace inside code.
2. Run the validator over each pair and paste the (empty) output into
   the PR description.
3. Open the PR against `main`. A reviewer fluent in the target locale
   must approve before merge; the reviewer reads the diff side by side
   with the English source and spot-checks technical terminology.
4. CI re-runs the validator and loader tests. Any protected-span drift
   fails the build, so reviewers never merge broken translations by
   accident.

## Serving translations

`GET /api/learning/modules/{slug}?lang=hu` returns the module with
overridden sections merged in; without the parameter (or after fallback
to English) the response is the plain English module. Responses carry a
`locale` field naming the locale actually served, so clients can tell a
fallback from a real translation.

Quiz questions, explanations, cheat sheets, summaries, and objectives
remain English in this phase; widening their coverage is future work and
should extend both the override schema and the validator's checked pairs.
